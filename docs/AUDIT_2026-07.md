# StatSnap — Portfolio Audit (July 2026)

Audit performed as a Principal SWE / sports-tech hiring-manager review, against
the live deployment (Render), the MongoDB Atlas database, and the full source
tree on `develop`. Findings within each section are ordered by importance.

**Scope note:** This is a V1 bootcamp capstone by design. Findings are graded
on portfolio impact — what a sports-tech interviewer (PFF, SumerSports,
Teamworks) would notice — not on production-readiness.

---

## 1. The "Hiring Manager" Impression

**Landing page: 8.5 / 10 · Player dashboard: 8 / 10**

### What lands (the wow factor)

- **The identity is real.** Dark brutalist, JetBrains Mono numerals, lime
  accent, 90° corners, terminal-style `>` prompt with a `⌘K` hint. This does
  not look like a template or a Tailwind starter — it looks *designed*, and
  design consistency is the single strongest first-impression signal a
  portfolio project can send.
- **The live schedule rail** immediately says "this app talks to real,
  current data." WK 1, kickoff times in local time, 16 games — a reviewer
  instantly understands there's a live pipeline behind it.
- **The search experience is genuinely fast** (~180 ms warm, 200 ms debounce,
  keyboard nav, recents chips persisted in localStorage). "Instant lookup" is
  the promise on the tagline and the app keeps it.
- **The dashboard density is right.** Headline stat row → click-to-swap
  sparkline → by-week rail → tabs. Percentile bars on the Advanced tab with a
  click-to-open glossary is exactly the kind of feature a PFF interviewer will
  poke at, and it holds up.
- Bye weeks are correctly *absent* from the game log (W9 → W11) rather than
  rendered as zero rows — a subtle correctness signal.

### What looks unpolished

1. **The 22-second cold start is the single biggest impression-killer.**
   Measured live: first request to the API after idle took **22.4 s** (Render
   free tier spin-down); warm requests are ~180 ms. A hiring manager clicking
   your resume link gets a dead search box and no explanation. Fixes, in
   order of cheapness: (a) show an explicit "waking the free-tier server,
   ~20 s" state in the UI when a request exceeds ~3 s; (b) an external
   keep-alive ping (UptimeRobot at 10-min intervals); (c) the $7/mo Render
   tier. Do (a) regardless — handling infrastructure reality in the UX is
   itself a portfolio point.
2. **Schedule rail overlap bug:** the `+5 MORE →` indicator renders on top of
   the last visible game card (ARI card, top-right). The `.sched-fade`
   overlay and the count pill collide with card content instead of fading it
   out. Small, but it's on the landing page — the first screen everyone sees.
3. **Percentile bars are unlabeled.** The Advanced tab bars clearly encode
   *something*, but nothing says "87th percentile" — the number shown at the
   right edge is the raw stat value. A viewer who doesn't click `? KEY` may
   read the bar as a progress meter of the raw value. Render the percentile
   number at the end of the fill (e.g. `P87`) — it's one span.
4. **`document.title` is always "StatSnap"** and there are no
   description/OpenGraph meta tags. Sharing a player page into Slack/LinkedIn
   (which is exactly how you'll share this with employers) produces a bare,
   title-less unfurl. `document.title = "Patrick Mahomes · StatSnap"` on the
   player page is a 5-line fix with outsized shareability payoff.
5. Minor display nits: **"Sack Yards Lost: -193"** — the metric name already
   says "lost," so the negative sign reads as a double negative (show `193`
   or relabel); **CPOE renders unsigned** (`0.3%`) even though it's an
   over/under-expected stat where the sign is the story (`+0.3%`).

## 2. Data & Analytics Logic Check

### What's genuinely strong

This is the best part of the project, and you should know that going into
interviews:

- **Schema fits the access pattern.** One document per player-season with an
  embedded `weeks` array means the player page is a single indexed `find`.
  Verified live: `{ playerId: 1, season: -1 }` compound index exists in
  Atlas; 5,873 docs across 10 seasons (2016–2025), all complete through week
  17/18; a full 10-season player payload is 122 KB raw → 14 KB over the wire
  (Brotli via Render's proxy). All within a comfortable envelope.
- **The aggregation discipline is real.** Ratio-of-sums for rate stats,
  attempt-weighted CPOE with null weeks dropped from both numerator and
  denominator, EPA-per-play with the same null-out pattern, cohort
  percentiles with qualifier gates and average-rank tie handling, inverted
  metrics ranked descending rather than `1 − p`. This is more statistical
  care than most senior take-home submissions show.
- **The ETL is idempotent** (bulk `UpdateOne` + `$set` + upsert keyed on
  `{playerId, season}`), NaN→null handling is explicit and commented, and the
  schedules join does a per-team pivot with a mismatch audit warning.

### Gaps found (ordered by severity)

1. **Search regex injection → 500 with leaked internals (confirmed live).**
   `controllers/players.js:14` passes raw user input into `$regex`. Tested
   against production: `?q=(mahomes` returns **HTTP 500** with body
   `{"message":"Regular expression is invalid: missing closing parenthesis"}`
   — a raw MongoDB error surfaced to the client via the error handler's
   `err.message` passthrough. `?q=.*` matches every player. Fix: escape regex
   metacharacters (`q.replace(/[.*+?^${}()|[\]\\]/g, "\\$&")`), anchor as a
   prefix match (`^` + escaped input), and have the error handler only expose
   `err.message` for errors with an explicit status. This is a 10-line fix
   and the #1 thing a backend interviewer would flag.
2. **`seasonComplete` is referenced but never exists.**
   `AdvancedPanel.jsx:33` reads `player.seasonComplete === false`, but no
   ETL stage, model field, or controller ever writes it — the field exists
   nowhere else in the codebase (verified by grep). Consequence: the
   "percentiles pending — not enough games yet" state is unreachable dead
   code, and a mid-season player below the qualifier gate is told they
   "didn't reach the qualifying threshold this season" while the season is
   still running. Either compute `seasonComplete` in the ETL (e.g. max week
   loaded ≥ 18) or remove the branch.
3. **README overclaims the ratio-of-sums doctrine.** The README says rates
   are "never the mean of per-week rates," but `targetShare`,
   `airYardsShare`, and `WOPR` are exactly that — documented as AVERAGE
   metrics in `percentiles.py` and mirrored with `averageWeeks()` in
   `stats.js`. The two implementations are *consistent with each other*
   (good), but a sharp interviewer who reads the README and then the code
   catches the contradiction. The honest story: true ratio-of-sums for target
   share needs per-week *team* pass attempts, which aren't stored — a real,
   defensible limitation. Fix the README to name the exception, and keep the
   limitation in your back pocket as a "what would you improve" answer.
4. **Search runs an unindexed collection scan.** The unanchored
   case-insensitive regex can't use any index (and `displayName` has none) —
   confirmed via `explain()`: COLLSCAN over all 5,873 docs per keystroke.
   It's 8 ms today, so this is not a user-facing problem — but it's an
   O(collection) design that degrades linearly as seasons are added, and
   "how does your search scale" is a guaranteed interview question. See
   Resume Booster #1.
5. **The NFL week boundary table is a time bomb with no alarm.**
   `nflWeek.js` hand-maintains `SEASON_BOUNDARIES` for 2025/2026 only. In
   September 2027, `seasonForDate` returns 2026, `deriveNflWeek` returns
   null/garbage weeks, the refresh bails with `no-current-week`, and the
   landing rail silently serves a stale 2026 cache forever. The code comment
   acknowledges hand-maintenance; the gap is that failure is *silent*. Log
   loudly (or surface `fetchedAt` staleness in the UI) when the anchor
   falls outside the table.
6. **Minor:** `formatAge` parses `"1995-09-17"` as UTC midnight but compares
   with local-time getters — ages can be off by one on the player's actual
   birthday in western timezones. Cosmetic at worst.

### Schema verdict

Optimized for what V1 does — yes. The embedded-weeks tradeoff (leaderboards
need `$unwind`) is consciously accepted and written down in the ADR, which is
what matters. The one structural addition worth making before interviews: a
supporting index or search strategy for `displayName` (finding #4).

## 3. The Portfolio Edge — 3 Resume Boosters

Chosen for effort-to-talking-point ratio, and because each one converts an
existing weakness into a story:

1. **MongoDB Atlas Search autocomplete (converts the search findings into a
   feature).** Replace the regex `$match` with an Atlas Search `autocomplete`
   index on `displayName`: typo tolerance ("mahomse" → Mahomes), diacritic
   folding, prefix semantics, index-backed instead of COLLSCAN — and the
   regex-injection bug becomes unreachable by construction. It's a managed
   feature of the Atlas tier you already run, roughly a day of work, and it
   upgrades your search story from "I regex'd the collection" to "I evaluated
   regex vs. text index vs. Atlas Search and can explain the tradeoffs."
   Resume line: *"Sub-100 ms fuzzy player search over N seasons via Atlas
   Search autocomplete indexes."*

2. **Head-to-head player comparison with shareable URLs.** A `/compare/:idA/:idB`
   route rendering two players' percentile bars and sparklines side-by-side,
   position-gated to the same cohort. You already have every primitive
   (StatRow, Sparkline, AdvancedPanel rows, the percentile cohorts) — this is
   composition, not new infrastructure, and it's the feature every
   sports-tech product (PFF Premium, SumerSports) actually sells. Shareable
   deep links + the OpenGraph fix from §1 make it a demo you can drop
   directly into a job application. Resume line: *"Composable stat-primitive
   architecture enabled a two-player comparison view in <300 LOC."*

3. **Automate the ETL with GitHub Actions + data-quality gates.** Right now
   the Python ETL runs from your laptop when you remember. A scheduled
   workflow (Tue 6 AM ET, in-season) running `SEASON=$current python load.py`
   with post-load assertions — row-count delta bounds, null-rate thresholds,
   max-week sanity — plus a `lastLoadedAt` surfaced in the UI footer, turns
   "I have a script" into "I own an automated, monitored data pipeline."
   This is the exact shape of real sports-data engineering work, and it also
   defuses the §2.5 staleness risk. Resume line: *"Zero-touch weekly data
   pipeline with automated data-quality checks via GitHub Actions cron."*

**Honorable mention (do it if you have one spare afternoon):** client-side
response caching (TanStack Query or a 5-line module-level Map) so back-nav
and season re-visits render instantly, plus `Cache-Control`/ETag headers on
the API. Cheap, measurable, and gives you an HTTP-caching interview story.
A test suite is deliberately *not* listed here — it's in §5 as table stakes.

## 4. Performance & UX Polish

Measured against the live deployment:

| Concern | Measured | Verdict |
|---|---|---|
| API cold start | **22.4 s** | The one real problem (§1.1) |
| API warm response (search, schedule) | ~180 ms | Fine |
| Full 10-season player payload | 122 KB → 14 KB (Brotli) | Fine — fetch-all-seasons is a defensible tradeoff (instant season switching, one request) |
| Search DB execution | 8 ms (COLLSCAN, 5,873 docs) | Fine today; see §2.4 |
| Console errors on load/navigation | none | Clean |

What makes it feel "student project" vs. product, beyond the cold start:

1. **No cold-start UX handling** — the search box silently does nothing for
   20+ s. This is the same fix as §1.1 and worth doing first.
2. **Plain-text loading states** (`LOADING PLAYER...`). Consistent with the
   brutalist voice, so keep the aesthetic — but reserve layout (fixed-height
   containers or skeleton blocks in the identity/stat areas) so the page
   doesn't reflow when data lands.
3. **The `+5 MORE →` overlap** (§1.2) — visible on first paint of the
   landing page.
4. **No React error boundary.** An unexpected render error white-screens the
   whole SPA. One boundary around the routes with a branded "something broke"
   panel is ~20 lines and it's the difference between a crash and a designed
   failure state.
5. **Byes are skipped silently in the game log.** Correct data-wise, but a
   dim `W10 · BYE` row would show intent rather than looking like a gap.
6. **Unknown routes render an empty shell** — there's no `path="*"` route, so
   a typo'd URL shows the header over a blank page. A branded 404 with the
   search box is trivially cheap and on-voice.

Not observed (checked for and clean): no console errors, no failed requests,
tab switching is instant, sparkline/rail interactions have no perceptible lag,
season switching is instant (all seasons pre-fetched — the payload tradeoff
paying off).

*Caveat: I verified desktop rendering in Chrome. The responsive breakpoints
(64/52/30 rem) exist in the CSS but I couldn't drive the window below desktop
width via automation, so mobile is unverified in this audit — worth a manual
pass on a real phone before you send the link out.*

## 5. Interview Talking Points — Cheat Sheet

The three toughest technical stories in this codebase, with the shape of how
to tell each (problem → decision → tradeoff → receipt):

### 1. "One stat, one definition" — the cross-language aggregation contract

- **Hook:** "My passing-EPA number drifted between two tabs of the same page,
  and fixing it forced a design doctrine."
- **The story:** Weekly EPA from nflverse is a *per-game total*, not a rate.
  Averaging weekly totals produced neither a season total nor a per-play rate
  — so the Overview tab and the Advanced tab disagreed. The fix was
  ratio-of-sums everywhere (`Σ EPA / Σ attempts`), with null weeks excluded
  from both numerator *and* denominator (a bye must not contribute
  denominator attempts as if EPA were zero). Same doctrine for
  attempt-weighted CPOE.
- **The hard tradeoff:** the math now lives twice — `etl/percentiles.py`
  (Python/Polars, for percentile ranking) and `utils/stats.js` (JS, for raw
  display values) — as a deliberately mirrored contract, documented in the
  ADR. Alternative was precomputing every display value server-side; you kept
  raw weeks client-side so the sparkline/game-log/season-switching stay
  instant with one fetch.
- **Own the weakness before they find it:** the mirror has no automated test
  pinning the two implementations together, and target share / WOPR are
  documented exceptions (weekly-mean, because per-week team denominators
  aren't stored). "The first thing I'd add is a golden-file test: one JSON of
  weeks in, identical season aggregates out of both implementations." Saying
  this unprompted flips the biggest gap in the repo (zero tests) into
  engineering judgment.

### 2. Document modeling — one player-season document, weeks embedded

- **Hook:** "I designed the schema backwards from the page render."
- **The story:** the player page always needs identity + season summary +
  full game log together, so each document is one player-season with an
  embedded `weeks` array. One indexed query (`{playerId: 1, season: -1}`)
  returns exactly the render shape. Verified numbers you can quote: 5,873
  docs, 10 seasons, ~9 KB average, 14 KB compressed for a 10-season player.
- **The tradeoff you accepted:** cross-player single-week queries
  (leaderboards) need `$unwind` — consciously out of V1 scope, written in the
  ADR at decision time, with the V2 options (flat collection vs. pipeline)
  already sketched. The 16 MB document cap is a non-issue at ≤18 weeks/doc.
- **Bonus depth:** the search endpoint is where the schema bites back — one
  doc per player-*season* means search must dedupe players, hence the
  `$sort → $group/$first` pipeline that returns each player with their most
  recent team. Schema choices propagate into query shapes; you can show you
  understood where.

### 3. The third-party API cache — cost decoupling and deriving what the API won't tell you

- **Hook:** "The Odds API gives you 500 credits a month and never tells you
  what NFL week it is. I made user traffic cost zero credits."
- **The story:** a `node-cron` job inside the Express process is the *only*
  caller of The Odds API (daily 08:00 UTC + boot). It writes one cache doc
  per `{season, week}`; `GET /schedule` reads only the cache. API cost tracks
  the cron schedule, not traffic; an upstream outage can never break a user
  request; empty upstream responses are refused so a good cache is never
  overwritten (self-healing floor).
- **The subtle part interviewers will enjoy:** the API returns kickoff
  timestamps, not week numbers. Naive Thursday-anchored bucketing breaks on
  the 2026 Wednesday opener. Tuesday noon ET is the one slot the NFL
  effectively never schedules into, so bucketing against Tuesday-noon
  boundaries classifies Wednesday openers, MNF/TNF, Saturdays, and
  international games with zero per-game special cases — validated against
  the real 2026 Week 1 slate.
- **Own the weakness:** the boundary table is hand-maintained per season and
  fails *silently* when the season rolls past it (§2.5) — name it and the fix
  (loud staleness alerting) before they ask.
